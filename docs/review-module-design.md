# 复盘模块设计

把《复盘自己：从记录到蜕变的行动指南》（[日] 山田智惠 著，王佳宝 译，机械工业出版社 2026-03）的方法论，
落成 LifeOS 里一个可用的模块。

- 状态：V1 已实现（周复盘四步向导 + 模式库），月复盘待做
- 记录时间：2026-11-01

## 一、这本书到底在讲什么

### 1. 它反对什么

书里点名了三种「复盘误解」，每一种都能在现有 LifeOS 里找到影子：

| 误解 | 后果 | 书里的反驳 |
| --- | --- | --- |
| 复盘 = 自我检讨 | 越复盘越自责，最后干脆不复盘 | 复盘的对象是**事实和行为**，不是人格。目标是优化下一步动作，不是情绪批判 |
| 复盘必须先有明确目标 | 没有目标就不开始，或者硬套一个假目标 | 现实充满变数，目标恰恰是在一次次回看中**逐渐显影**的 |
| 复盘是成功者的工具 | 普通人觉得自己没什么可复的 | 越是缺规划、缺资源的人，越需要靠复盘兜住变化 |

### 2. 它主张什么

一句话：**复盘不是找缺点，是发现自己早已拥有、但没被看见的资源。**

机制叫「认知重构」——把三类模糊的东西变成清晰的东西：

- 模糊的情绪 → 能被说清楚的情绪
- 零散的经历 → 有结构的经历
- 隐性的特质 → 能被调用的能力

所以它的产出不是「我下次要改什么」，而是「我原来是这样一个人，我手里有什么」。

### 3. 三个深度阶段（树的比喻）

| 阶段 | 时间 | 在看什么 |
| --- | --- | --- |
| 枝叶可见期 | 3 个月 – 半年 | 如实记录当下的情绪、在意的事、身边的人。关键动作是**不美化** |
| 树干可见期 | 记录成为习惯之后 | 浮现出核心特质：兴趣、优势、反复出现的行为模式 |
| 根系可见期 | 更深一层 | 挖到模式背后的底层信念，看清真正想要的东西 |

这个比喻的实操含义是：**不能跳级**。没有几个月的诚实记录，直接去挖「底层信念」只会挖出自己想听的答案。

### 4. 七种技巧

| 技巧 | 做什么 |
| --- | --- |
| 切分 | 区分可控与不可控，把精力收回到能改变的部分 |
| 意义重塑 | 换个解读角度，从挫折里挖出积极意义 |
| 聚焦 | 不面面俱到，只挑对结果影响最大的事深挖 |
| 联结 | 把多件事串起来，找反复出现的根本问题 |
| 抽象化 | 从单次经历提炼成可复用的能力或规律 |
| 具体化 | 把结论落成明确、可执行的行动 |
| 视角切换 | 跳出当局者视角，用旁观者或未来视角看自己 |

前四个偏「看清」，后三个偏「转化」。抽象化和具体化是一对：一个往上收成规律，一个往下落成动作。

### 5. 三类复盘方式

- **每日**：第一步如实记录事件和感受，第二步复盘记录的内容
- **周度**：① 聚焦本周最重要的 3 件事 → ② 找出「联结」并标注 → ③ 抽象化 → ④ 具体化
- **月度**：在抽象化与具体化之间切换，让想法真正落地

日、周、月不是三套独立流程，是同一条流水线的三个工位：日负责**采集**，周负责**加工**，月负责**定型**。

### 6. 关于习惯

书里专门有一章讲「别让复盘变成负担」：可以中断、可以只写一点、容易自责时切到「哲学模式」。
这条约束在设计时要当真——一个要求每天填满的系统，最后一定会被放弃。

## 二、现有 LifeOS 缺什么

对照下来，缺口很明确，而且不是「少一个表单」：

| 书里的环节 | LifeOS 现状 | 缺口 |
| --- | --- | --- |
| 每日如实记录 | `checkins` 已有 plan + q1–q6 + review | 有，但偏检讨 |
| 聚焦 / 联结 | 无 | **日记是一条条孤岛，跨天看只能靠翻** |
| 抽象化 | 无 | 结论没有沉淀物，写完就散了 |
| 具体化 | `items` 清单 | 有容器，但没有从复盘中产生的通路 |
| 周复盘 | 无 | 缺失 |
| 月复盘 | 无 | 缺失 |
| 视角切换 / 意义重塑 / 切分 | 无 | 缺失 |

**核心判断**：现在系统停在「枝叶可见期」——记录了，但永远看不到树干。

而且有一处价值取向上的冲突值得指出：`belief.ts` 的六个问题（恐惧识别、旧信念、逃避、弱点）
本质上是**检讨式**的，正是这本书批评的形态。它有用，但如果整个系统只有它，
长期会强化「我总是在逃避」这个叙事。

复盘模块的一个隐性职责，就是提供**反向证据**：这周你做成了什么、什么在起作用。

## 三、模块设计

### 3.1 一句话

> 日记是原料，周复盘是加工，模式卡是资产。

模块的价值不在于多一个填写页，而在于把散落的日记**蒸馏成可以反复引用的自我认知**。

### 3.2 三层结构

```
每日  checkins（已有）        采集：事件 + 感受 + 计划
  ↓
每周  reviews (week)          加工：聚焦 3 件 → 联结 → 抽象化 → 具体化
  ↓
每月  reviews (month)         定型：模式验证、方向校准
  ↓
长期  patterns                 资产：可复用的模式卡，证据持续累积
```

### 3.3 核心设计决策：把七种技巧变成界面的动作

这是整个设计最重要的一条。**七种技巧如果只写成提示语，用户不会用。**

每一种技巧都要在 UI 上变成一个**必须做的动作**：

| 技巧 | 界面上的形态 |
| --- | --- |
| 聚焦 | 从本周日记里勾选，**选满 3 条后其余禁用** |
| 联结 | 3 张卡片并排，中间连线，下方填「它们的共同点」 |
| 抽象化 | 共同点 → 一句可复用的话，落成一张**模式卡** |
| 具体化 | 模式卡下方生成 1–3 个行动项，一键写入 `items` |
| 切分 | 每条选中事件旁一个「可控 / 不可控」二选一 |
| 意义重塑 | 标记为负面的事件展开一个「换个说法」输入框 |
| 视角切换 | 卡片右上角「一年后的我」按钮，切换提问角度 |

### 3.4 模式卡（patterns）—— 模块的核心资产

这是让复盘产生复利的东西。一张模式卡包含：

| 字段 | 含义 | 对应书中 |
| --- | --- | --- |
| 触发条件 | 什么情况下会出现 | 树干 |
| 我的反应 | 我通常怎么做 | 树干 |
| 短期收益 | 它保护了我什么 | 意义重塑 |
| 长期代价 | 我为此付出了什么 | 根系 |
| 替代动作 | 下次可以怎么做 | 具体化 |
| 证据 | 关联的日期列表，可点回当天 | 枝叶 |
| 状态 | 观察中 / 已验证 / 已放下 | 根系 |

「短期收益」这一栏是关键。它逼你承认：拖延、回避、讨好都不是无理由的，
它们在某个时刻确实保护过你。承认这一点，模式才拆得掉。

### 3.5 数据模型

两张新表。`evidence` 用 JSON 数组存日期，不单独建关联表——
因为前端本来就是 `/api/bootstrap` 一次性拉全量，不需要 SQL 层 join。

```sql
CREATE TABLE reviews (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,
  period_type TEXT NOT NULL,   -- 'week' | 'month'
  period_key TEXT NOT NULL,    -- '2026-W44' | '2026-11'
  data TEXT NOT NULL,          -- JSON，见下
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE UNIQUE INDEX reviews_user_period_uq ON reviews (user_id, period_type, period_key);

CREATE TABLE patterns (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,
  title TEXT NOT NULL,
  trigger TEXT,
  reaction TEXT,
  payoff TEXT,
  cost TEXT,
  alternative TEXT,
  evidence TEXT NOT NULL DEFAULT '[]',  -- JSON: ["2026-10-28", ...]
  status TEXT NOT NULL DEFAULT 'watching', -- watching | verified | retired
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX patterns_user_status_idx ON patterns (user_id, status);
```

`reviews.data` 的形状：

```ts
type ReviewData = {
  focus: string[];              // 选中的 checkin 日期，最多 3 条
  connection: string;           // 这些事有什么共同点
  abstraction: string;          // 提炼出的规律
  actions: string[];            // 具体动作
  patternIds: string[];         // 关联或新建的模式卡
  controllable?: Record<string, "in" | "out">; // 切分：日期 → 可控/不可控
  reframe?: Record<string, string>;            // 意义重塑：日期 → 换个说法
  wins?: string;                // 本周做成了什么（对抗检讨倾向）
};
```

### 3.6 API

沿用现有模式，扩展 bootstrap 而不是新增一堆拉取接口：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/bootstrap` | **扩展**：响应增加 `reviews`、`patterns` |
| GET | `/api/reviews?type=week` | 按类型读取 |
| GET | `/api/reviews/:type/:key` | 读取单篇 |
| PUT | `/api/reviews/:type/:key` | 保存（upsert，允许半成品） |
| GET | `/api/patterns` | 读取模式库 |
| POST | `/api/patterns` | 新建模式卡 |
| PATCH | `/api/patterns/:id` | 修改（含状态流转、追加证据） |
| DELETE | `/api/patterns/:id` | 删除 |

### 3.7 页面

新增导航项「复盘」，位置在「日记」之后。

| 路由 | 内容 |
| --- | --- |
| `/review` | 复盘首页：本周状态、连续周数、模式库概览、进入向导 |
| `/review/week/:key` | 周复盘四步向导 |
| `/review/month/:key` | 月复盘（复用向导组件，周期不同） |

周复盘向导的四个步骤：

1. **取材** — 自动列出该周 7 条日记（含 plan、q1–q6 摘要、review）
2. **聚焦** — 勾选最重要的 3 件，选满即禁用其余；每条可标可控/不可控
3. **联结** — 3 张卡并排，填共同点；可挂到已有模式，或新建
4. **落地** — 写一句抽象化结论 + 1–3 个行动项，一键写入 `items`

每步都可以单独保存，不要求一次写完。

## 四、分阶段落地

| 版本 | 范围 | 理由 |
| --- | --- | --- |
| V1 | `reviews` + `patterns` 表、周复盘四步向导、复盘首页 | 主链路闭环 |
| V2 | 月复盘 | 复用向导组件，成本低 |
| V3 | 切分 / 意义重塑 / 视角切换 三个辅助动作 | 锦上添花，不影响主链路 |
| V4 | 模式复利提示（「这个模式第 5 次出现」） | 需要数据积累才有意义 |

## 五、风险与取舍

1. **周复盘比日复盘重，完成率一定更低。**
   对策：分步保存 + 允许只做前两步。不要设计成「必须四步全填」。

2. **模式卡会通货膨胀。**
   对策：同时处于「观察中」的状态上限 5 条，超了必须先收掉一条。少而深胜过多而浅。

3. **和信念重写的检讨倾向打架。**
   对策：周复盘第一步之后强制插入「本周做成了什么」，先给证据再给问题。

4. **不要自动生成模式。**
   自动提炼会让人失去「自己想明白」的那一下，而那一下才是复盘的全部价值。
   可以做的是提示「这个模式已经出现 5 次」，不做的是替你下结论。

5. **月复盘容易变成年度总结的缩水版。**
   对策：月复盘只回答一个问题——「哪些模式被验证了，哪些被推翻了」。不重新写一遍人生。
