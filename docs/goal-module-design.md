# 目标模块设计：给五步诊断一个落脚点

把「设定不同目标，每个目标单独走一遍五步诊断」落成 LifeOS 里的一个模块。
人生 OS 负责给大方向，目标模块负责把方向翻译成可以被诊断、被验证的对象。

- 状态：V1 已实现（本地验证通过，待部署）
- 记录时间：2026-11-03
- 已确认：按 V1 全量开工；「投资」可以直接作为一个目标，领域只是可选分类
- 相关文档：[复盘模块设计](review-module-design.md)

## 一、现在缺的是什么

改造前，五步诊断只是 `/principles` 的静态说明页；人生 OS 是六栏长文。两者之间没有承接物：

| 层 | 现在有什么 | 缺什么 |
| --- | --- | --- |
| 方向 | 人生 OS 六栏：我是谁、我在哪、我要去哪、差在哪、怎么走、怎么验证 | 一段能被引用、能对齐的「大方向」 |
| 问题 | 五步诊断的静态方法论 | 「哪个问题」——没有具体目标，五步无处落脚 |
| 行动 | 每日仪式、清单、周复盘 | 行动和目标之间没有一条可回看的线 |

所以不是「再加一个表单」，而是补一层**目标**：

> 人生 OS 定方向，目标定战场，五步诊断做推理，践行日志做验证。

## 二、三层结构

```
人生 OS（方向）
  方向卡：3–5 年方向 / 12 个月主题 / 今年最重要的赌注 / 明确不做
        ↓ 对齐
目标（战场）
  领域：投资 / 事业 / 健康 / 关系 / 学习 / 人生 / 其他
  每个目标：期限、成功标准、愿意交换什么
        ↓ 逐个走
五步诊断（推理）
  目标 → 问题 → 诊断 → 方案 → 践行
        ↓ 验证
践行日志（证据）
  每次记录：做了什么 / 结果 / 偏差 / 下一步
        ↓ 回看
复盘 / 模式库（已有）
```

一个关键决定：**一个目标一条诊断线**。

「投资」可以直接作为一个目标，也可以先选「投资」领域再拆成多个更具体的目标。
领域只是可选分类，不强制先拆领域；一个目标可以就叫「投资」，五步都围绕它展开。
同一个领域下如果有多个目标，各自独立完成五步，不能共用一份诊断。

## 三、什么才算一个目标

三个判定，缺一不可：

1. **可验证**：达成时能被证据检查，不是「感觉好一点」。
2. **有期限**：90 天 / 1 年 / 3 年，不能是「以后」。
3. **有交换**：写得出愿意放弃什么。只想要结果、不愿付出代价的是欲望。

反例：

| 写法 | 为什么不是目标 |
| --- | --- |
| 我想变有钱 | 是愿望，没有标准、期限和交换 |
| 投资 | 如果只是一个话题，没有期限、标准和代价，就还停在领域层面 |
| 每天看财报 | 是动作，不是结果 |
| 18 个月内建立一套能穿越周期的投资体系，最大回撤控制在 20% 以内 | 是目标：有期限、有成功标准、有代价 |

产品不阻止用户写错，但第 1 步的提示语和完成条件要把这个标准讲清楚。

## 四、用户流程

1. **写方向卡**（人生 OS 顶部）：3–5 年方向、12 个月主题、今年最重要的赌注、明确不做。
2. **建目标**：写名称；领域、期限可选。新目标直接进入「进行中」。
3. **走五步**：每步只卡 1–2 个关键字段，其余是追问；每一步都能单独保存。
4. **记录践行**：第 5 步写一条记录，带证据、偏差和下一步。
5. **收束**：根据真实结果继续 / 调整 / 达成 / 放下，改目标状态。

## 五、页面与交互

### 5.1 `/principles` 目标列表（替换原来的静态页）

从上到下：

1. **方向卡摘要**：显示人生 OS 的 12 个月主题 + 方向一句话；没写就提示先去写。
2. **指标条**：进行中目标数 / 走完五步的目标数 / 最近一次践行。
3. **筛选**：状态（当前 / 已暂停 / 已结束 / 全部）+ 领域 chips（只显示已有目标的领域）。
4. **目标卡网格**：领域图标、标题、状态、五步进度、当前卡点、期限、最近践行。
5. **五步方法说明**：五张短卡，保留原静态页的方法论。
6. **新建目标**：按钮打开轻量对话框（名称 + 可选领域 / 期限），创建后直接进入第 1 步。

目标卡上的「当前卡点」取第一个未完成的步骤，例如「卡在第 3 步 · 诊断根源」。
这比显示「完成 60%」更能推动下一步。

### 5.2 `/principles/:goalId` 单目标五步诊断

- 顶部：返回、目标标题（可直接改）、领域 / 状态选择、五步进度条。
- 步骤条：5 个 tab，可点击跳转；完成的步骤打勾；当前步骤高亮。
  步骤放在 URL `?step=1..5`，刷新能回到原处。
- 主区：当前步骤的字段；每步顶部写「这一步的产出」，底部「上一步 / 下一步」。
- 右侧：
  - 这一步还差什么（完成条件清单）
  - 大方向（人生 OS 摘要 + 链接）
  - 目标速览（期限、挑战度、关键问题、践行次数、上次践行）
  - 删除目标（二次确认）
- 自动保存：输入停下 800ms 后保存；显示「保存中 / 已保存 14:32 / 保存失败，点击重试」；
  有未保存内容时离开页面会提示。
- 空状态：第 3 步没有关键问题时，不让人硬写，直接引导回第 2 步选一个。

### 5.3 人生 OS 的方向卡

在 `/lifeos` 六栏之上加一张独立的「方向卡」，仍然存 `documents`：

- 3–5 年，我想把人生带到哪里？
- 未来 12 个月的主题
- 今年最重要的一个赌注
- 我明确不做什么

不并进六栏。六栏是「认识自己」，方向卡是「给出坐标」；混在一起会又变成一篇长文。
方向卡保存后，目标页直接引用，不用复制粘贴。

### 5.4 总览

加一条「进行中的目标」：最多显示 3 个目标 + 五步进度 + 下一步；没有目标时给创建入口。
快捷入口加「🎯 五步诊断」。

## 六、五步的字段

### 第 1 步 · 目标

| 字段 | 提示 | 完成条件 |
| --- | --- | --- |
| 目标陈述 | 在什么期限内，把什么从什么状态变成什么状态 | 必填 |
| 为什么是现在 | 如果今年不做，会失去什么 | 选填 |
| 成功标准 | 达成时能被谁、用什么证据验证（1–5 条） | 至少 1 条 |
| 愿意交换什么 | 要放弃的时间、舒适、机会 | 选填 |
| 明确不做 | 为了它，我决定不做什么（1–5 条） | 选填 |
| 期限 | 日期 | 选填 |
| 挑战度 | 1–10 | 选填 |
| 方向对齐 | 它服务于人生 OS 的哪个方向 | 选填 |

### 第 2 步 · 问题

问题卡（1–5 张）：

- 问题一句话
- 证据 / 现象（具体到次数、场景、数字）
- 影响：高 / 中 / 低
- 可控性：可控 / 部分可控 / 不可控
- 设为关键问题（单选）

完成条件：至少 1 张问题卡 + 选中 1 个关键问题。下一步只诊断这一个。

### 第 3 步 · 诊断

| 字段 | 提示 | 完成条件 |
| --- | --- | --- |
| 直接原因 | 表面上看，是什么直接造成的 | 选填 |
| 为什么链 | 连续追问 3–5 次，直到答案变成可改变的结构 | 选填 |
| 根本原因 | 不是「我不够努力」；写能力、环境、资源、关系或信念上的结构 | 必填 |
| 反复出现的模式 | 这个问题以前在哪里出现过 | 选填 |
| 另一种解释 | 如果旧判断是错的，还有什么解释 | 选填 |
| 诊断结论 | 真正的问题不是 X，而是 Y | 必填 |

### 第 4 步 · 方案

| 字段 | 提示 | 完成条件 |
| --- | --- | --- |
| 策略 | 如果只能做一件事，做什么 | 必填 |
| 方案自检 | 这个方案在解决根本原因，还是缓解症状 | 选填 |
| 90 天里程碑 | 1–3 个，可勾完成 | 至少 1 个里程碑或 1 条周动作 |
| 每周动作 | 每周可重复执行的动作，不是待办清单（3–5 条） | 同上 |
| 每日动作 | 1–3 条 | 选填 |
| 障碍预演 | 当……发生时，我就……（1–3 组） | 选填 |
| 验证指标 | 指标 / 目标值 / 频率（1–3 个） | 选填 |
| 停止做的事 | 为了这个方案，必须停掉什么 | 选填 |

### 第 5 步 · 践行

- 每次记录一条：日期、做了什么、结果 / 证据、偏差 / 卡点、下一步。
- 记录按时间倒序展示，可删除。
- 阶段结论：这一阶段验证出了什么；接下来继续 / 调整 / 停止。
- 状态操作：暂停 / 标记达成 / 放下。
- 完成条件：至少 1 条践行记录。

完成度是**推导**出来的，不做手动勾选。
这样「完成」永远对应真实内容，不会出现「全勾了但都是空的」。

## 七、完成度、状态与提醒

- 五步完成度 = 5 个步骤的完成条件命中数 / 5。
- 当前卡点 = 第一个未完成步骤；全完成则显示「进入践行」。
- 目标状态：`draft` 草稿 / `active` 进行中 / `paused` 暂停 / `achieved` 已达成 / `archived` 已放下。
- 同时进行中的目标建议不超过 3 个；超过只提示，不硬拦。
- 进行中且 14 天没有践行记录 → 列表打「14 天没记录」标记；不催办，只提示。

## 八、数据模型

### 8.1 新表 `goals`

```sql
CREATE TABLE goals (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,
  title TEXT NOT NULL,
  domain TEXT NOT NULL DEFAULT 'other',
  status TEXT NOT NULL DEFAULT 'active',
  data TEXT NOT NULL DEFAULT '{}',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE INDEX goals_user_status_idx ON goals (user_id, status);
CREATE INDEX goals_user_updated_idx ON goals (user_id, updated_at);
```

为什么不复用 `documents`：目标需要列表、筛选、状态、排序和独立 id；
`documents` 适合「一篇一篇的长文」，不适合「一组可枚举的对象」。
方向卡仍然用 `documents`（`module = "lifeos"`, `key = "direction"`），因为它是单篇。

### 8.2 `data` 形状

```ts
type GoalData = {
  version: 1;
  goal: {
    statement: string;
    whyNow: string;
    successCriteria: string[];
    tradeoffs: string;
    notDoing: string[];
    deadline: string;       // YYYY-MM-DD
    alignment: string;
    challenge: number;      // 1–10
  };
  problem: {
    items: GoalProblem[];
    keyProblemId: string | null;
  };
  diagnosis: {
    directCause: string;
    whyChain: string[];
    rootCause: string;
    pattern: string;
    alternative: string;
    conclusion: string;
  };
  plan: {
    strategy: string;
    check: string;
    milestones: GoalMilestone[];
    weeklyActions: string[];
    dailyActions: string[];
    ifThen: GoalIfThen[];
    metrics: GoalMetric[];
    stopDoing: string[];
  };
  practice: {
    logs: GoalPracticeLog[];
    review: string;
    nextStep: string;
  };
};
```

子结构：

| 类型 | 字段 |
| --- | --- |
| `GoalProblem` | `id, title, evidence, impact: high/medium/low, control: in/partial/out` |
| `GoalMilestone` | `id, text, due, done` |
| `GoalIfThen` | `id, trigger, response` |
| `GoalMetric` | `id, name, target, cadence` |
| `GoalPracticeLog` | `id, date, did, evidence, gap, next` |

### 8.3 API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/bootstrap` | 扩展：响应增加 `goals` |
| GET | `/api/export` | 扩展：导出增加 `goals` |
| GET | `/api/goals` | 读取全部（bootstrap 已够，保留给独立刷新） |
| GET | `/api/goals/:id` | 读取单个目标 |
| POST | `/api/goals` | 新建 |
| PATCH | `/api/goals/:id` | 改标题 / 领域 / 状态 / `data`（整段替换） |
| DELETE | `/api/goals/:id` | 删除 |

- `data` 由客户端整段提交，服务端只做 JSON 对象校验和大小上限。
  步骤字段的产品校验放前端，避免每加一个字段就改一次服务端 schema。
- 保存成功后用 `setQueryData` 更新缓存，不整页 refetch，避免自动保存时输入被重置。
- 冲突策略：单人使用，最后写入覆盖；返回更新后的 `updatedAt`。

## 十、分期

| 版本 | 范围 | 理由 |
| --- | --- | --- |
| V1 | `goals` 表、API、方向卡、目标列表、五步诊断、践行日志、总览入口 | 主链路闭环 |
| V1.1 | 每周动作写入清单 / 每日仪式；诊断关联模式卡；周复盘展示进行中目标 | 跨模块复利，但依赖 V1 数据 |
| V2 | 指标趋势、决策历史、目标模板、月度目标复盘 | 有数据积累后再做 |

V1 明确不做：

- AI 自动生成目标、诊断结论或方案。
- 多人协作、分享、评论。
- 复杂的项目管理能力（依赖、甘特图、提醒推送）。

## 十一、风险与取舍

1. **字段多，填写重。**
   对策：分五步；每步只卡 1–2 个关键字段；自动保存；随时可以只写一半。
2. **目标会膨胀。**
   对策：进行中软上限 3 个；暂停 / 归档；列表只突出「当前卡点」，不堆指标。
3. **和复盘重叠。**
   对策：复盘看已经发生的事，诊断看还没发生的事。诊断结论可以成为周复盘的输入，
   但不自动生成，也不把复盘表复制一遍。
4. **人生 OS 太长，目标引用不到。**
   对策：方向卡独立、短、结构化；目标页只展示摘要 + 链接。
5. **目标太泛，无法诊断。**
   对策：允许「投资」直接作为一个目标，但第 1 步要求补上期限、成功标准和愿意交换什么；
   领域只是可选分类，不强制先拆。
6. **自动保存的竞态。**
   对策：单人、整段提交、最后写入覆盖；失败可见、可重试；离开前提示。
7. **不要替用户下结论。**
   诊断的价值在「自己想明白」的那一下。V1 只提供问题和结构，不提供答案。

## 十二、实现备注

- V1 已按本设计落地：`goals` 表、目标 CRUD、方向卡、目标列表、五步工作台、践行日志、总览入口。
- 「投资」可以直接作为目标；新建时如果没选领域，标题里出现「投资」「健康」「学习」等词会自动归类。
- 导航保留「五步诊断」；`/principles` 是目标列表，`/principles/:goalId` 是单目标工作台。
- 五步完成度由内容推导，不存额外状态字段。
- 自动保存 800ms 防抖，保存失败会停下等待手动重试，不会连续重试打接口。
